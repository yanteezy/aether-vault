# CLAUDE.md — правила проєкту Aether

> Цей файл читається на початку кожної сесії. Тримай його актуальним: якщо змінюєш архітектуру — онови відповідний розділ тут у тому ж коміті.

## Що це за проєкт

**Aether** — десктопний застосунок для нотаток з просторовим полотном (spatial canvas).
Мета: об'єднати сильні сторони Notion (структура, бази даних, види) та Obsidian (локальні Markdown-файли, посилання, граф) навколо головної переваги Aether — живого полотна. Принцип: **один запис — багато видів** (полотно, документ, таблиця, канбан, календар, граф, галерея показують ті самі дані).

- Репозиторій: `yanteezy/aether-vault` (публічний — так треба для оновлень). **Ніколи не створюй новий репозиторій**, особливо з назвою `aethel-vault`.
- Мова інтерфейсу: українська (джерело), англійська — переклад.
- Користувач спілкується українською. Відповідай українською, код і коментарі в коді — англійською.

## Стек

- **Tauri 2** (Rust, `src-tauri/`) + **React 19** + **TypeScript** + **Vite**. Без UI-бібліотек: власні компоненти й CSS.
- Плагіни Tauri: updater, process, opener, deep-link, single-instance, dialog.
- Збірка релізів: GitHub Actions `.github/workflows/release.yml` (macOS universal + Windows NSIS), підпис оновлень minisign.

## Дані сховища

- Нотатки, зв'язки, рамки, кнопки-теги, малювання й вид полотна (`notes`, `connections`, `frames`, `chips`, `ink`, `canvas-transform`) мають одного власника — `VaultRepository` (`src/features/vaultRepo.ts`), один екземпляр на сховище (`getVaultRepo(id)`), спільний для всіх видів, що показують це сховище.
- **Усі види (полотно, документ, таблиця, канбан…) читають і пишуть ці дані тільки через репозиторій**: у React — `useVaultData(vault.id, kind, initial)`, поза React — `getVaultRepo(id).get/set/getNote/listNotes/updateNote/subscribe`. Не читай і не пиши ключі `vaultKey(id, …)` напряму, поки сховище відкрите (виняток — новий порожній `id`, якого ще ніхто не показує, як у `openSharedBoard`).
- Збереження як у `usePersistentState`: запис через 200 мс після останньої зміни, одразу на `aether:flush` / `beforeunload`, нічого після `suspendPersistence()`. Код, що читає сховище «повз» репозиторій (бекап), спершу робить `flush()` із `store.ts`.
- Репозиторій звільняється, коли сховище не показує жоден вид (відкладене дописується); `deleteVaultData` спершу скидає репозиторій без запису.
- Формат зберігання визначає `VaultBackend` (`load` / `save` / `remove`). Зараз — `KeyValueBackend`: ті самі JSON-ключі, що й у 0.2.x. Новий формат = новий бекенд + міграція (правило 1), а не зміни у видах.
- Стан інтерфейсу (`panel-graph`, `ink-tool`, `active-tag-filters`, …) — не дані сховища, він лишається на `usePersistentState`.

## Новий формат файлів (з 0.3; міграція поки лише в збірках з `VITE_FILE_VAULTS=1`)

Сховище = папка в папці даних: `<нотатка>.md`, `<полотно>.canvas` (JSON Canvas 1.0), `attachments/`, `.aether/vault.json`, `.aether/canvas-extra/<полотно>.json`, `.trash/`.

- Rust лише безпечно переносить текст і байти; вміст файлів складає й розбирає TypeScript (`src/features/formats/`).
- У `.md` — усе про саму нотатку (властивості `aether-*`, `tags`, `color`, `style`, `updated`); позиція й розмір — у `.canvas` (цілі пікселі); малюнки, кнопки-теги, кольори й замки рамок, вид — у `canvas-extra`.
- Приховані позначки `%% aether:body|checklist|code %%` пишуться лише там, де звичайний Markdown прочитався б інакше.
- **Не нищити чуже:** невідомі властивості frontmatter і чужий вміст `.canvas` зберігаються; файл із пошкодженим frontmatter не переписується (`bad-frontmatter`); з `.canvas` зникає лише те, що Aether сам прочитав або записав (`owned`, передавай його в наступний запис).
- `unreadable` у знімку сховища — це **не** видалені нотатки.
- Перемикання: `fileStore.ts` — `FileStore` є `VaultBackend` над `VaultFiles` (`vaultFiles.ts`); `migrateVaults.ts` вважає сховище перенесеним лише коли прочитане з файлів збігається зі старими даними. Позначка — ключ `storage-format`; щойно вона є, застосунок працює з файлами незалежно від прапорця. Старі ключі після міграції не змінюються.
- Код, якому потрібні дані сховища поза React, бере їх через `getVaultBackend()` — не через ключі `vaultKey(…)`.
- Перевіряючи міграцію на десктопі, запускай `tauri dev` з іншим `identifier` і схемою посилань (`--config`), інакше тестова збірка візьме справжню папку даних і перехопить `aether://`.
- Після навмисної зміни формату: `UPDATE_FIXTURES=1 npm test`.

## Незмінні правила

1. **Дані користувача — святе.** Будь-яка зміна формату збереження = міграція з автоматичним бекапом, старі файли не видаляються щонайменше дві версії, є шлях назад. Ніколи не запускай старт «з порожнього» поверх недоступних даних.
2. **Секрети.** Приватний ключ підпису `~/.tauri/aether.key` і його пароль — тільки в користувача. Не читай, не виводь, не комітить. Секрети GitHub: `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Не комітити `.env`, ключі, токени.
3. **Версія.** Кожна завершена зміна: `package.json` `version` +0.0.1; перший крок нової фази піднімає мінорну версію (напр. 0.2.x → 0.3.0, далі 0.3.1, 0.3.2…) (tauri.conf.json бере версію звідти) + рядок у `RELEASE_NOTES.md` зверху у форматі `• English text · Український текст`. Тег релізу = `v<version>` точно як у package.json.
4. **Переклади.** Кожен новий рядок інтерфейсу: `t('Український')` / `tr(...)` + запис у `src/i18n/en.ts`. Не використовуй один ключ для різних значень (приклад: «Скасувати» = Cancel, «Скасувати дію» = Undo).
5. **Доступність (WCAG 2.2 AA) — не регресувати:** справжні `<button>`/`<input>`, `aria-label` на кнопках-іконках, контраст ≥ 4.5:1, видимий фокус, усе доступне з клавіатури, цілі ≥ 24×24, `prefers-reduced-motion`, оголошення важливих дій через `announce()`.
6. **Не ламати наявне:** полотно, малювання, рамки, кнопки-теги, поширення посиланням, експорт/імпорт, папка даних, автооновлення, deep-link `aether://`.
7. **Без нових важких залежностей без пояснення.** Перед додаванням пакета — назви його, розмір, навіщо, альтернативу.
8. **Один крок — одна зміна.** Не роби «заодно» рефакторинг поза задачею. Помітив проблему поза задачею — запиши у відповідь, не виправляй.

## Як працювати в кожній сесії

1. Спершу **план**: які файли зміниш/створиш, нові типи, міграції, ризики, як перевіриш. Чекай «ок».
2. Пиши код невеликими комітами з осмисленими повідомленнями.
3. Перевірка перед завершенням (усе має бути зелене):
   - `npx tsc -b` — без помилок
   - `npm run lint`
   - `npm test` (Vitest) і `npm run test:e2e` (Playwright)
   - `cargo check` і `cargo test` у `src-tauri/` — якщо чіпав Rust (спершу `npm run build`: Tauri потрібна папка `dist`)
4. У фінальній відповіді: що зроблено, як перевірити руками (2–5 кроків), що свідомо не зроблено, нова версія.

## Тести

| Що | Команда | Де лежить |
| --- | --- | --- |
| Юніт-тести (Vitest + jsdom + fake-indexeddb) | `npm test`, у режимі стеження `npm run test:watch` | поруч із кодом: `src/**/<файл>.test.ts`; спільний setup — `src/test/` |
| Смоки в браузері (Playwright, Chromium) | `npm run test:e2e` (сам запускає `vite` на порту 1420) | `e2e/*.spec.ts`, стартовий стан — `e2e/fixtures.ts` |
| CI | на кожен push і PR | `.github/workflows/test.yml`: tsc, lint, test, test:e2e, `cargo check`, `cargo test` |

- Перший запуск на новому комп'ютері: `npm ci`, потім `npx playwright install chromium`.
- Тести йдуть у **браузерному режимі** (без Tauri, дані в localStorage / IndexedDB). Код, що кличе Rust, тестуй через `vi.mock('@tauri-apps/api/core')` (приклад — `src/features/store.test.ts`).
- Файл, якому не потрібен DOM, але потрібні справжні `Blob.stream()` / `CompressionStream`, — з рядком `// @vitest-environment node` (як `share.test.ts`).
- Типи тестів перевіряє `tsconfig.test.json` (входить у `npx tsc -b`); у збірку застосунку тести не потрапляють.
- **Правило: нова фіча = новий тест.** Логіка — юніт-тест; новий сценарій користувача — смок в `e2e/`. Виправлений баг — тест, що його ловить.

## Продуктивність (цілі)

- Сховище на 10 000 нотаток: відкриття < 1 с, пошук < 100 мс, прокрутка/масштаб полотна 60 fps.
- Не тримати весь вміст усіх сховищ у пам'яті без потреби; важкі обчислення — в Rust або Web Worker.

## Дизайн

- Темна тема «Скло» за замовчуванням, світла тема; акцентний колір налаштовується (`--accent`, `--accent-fill`, `--on-accent`).
- Новий UI будується за обраним концептом (див. промпт фази 4). До того — дотримуйся поточних стилів.
